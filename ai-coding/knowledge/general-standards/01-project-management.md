# 项目管理规范

## 1. 需求管理

### 1.1 需求文档
- **PRD（产品需求文档）**
  - 背景与目标
  - 用户画像与场景
  - 功能需求清单
  - 非功能需求（性能、安全）
  - 验收标准

### 1.2 需求评审
- **评审参与方**：产品、开发、测试、UI、运维
- **评审重点**：
  - 需求合理性
  - 技术可行性
  - 工作量评估
  - 风险识别

### 1.3 需求变更
- **变更流程**：
  1. 提交变更申请
  2. 影响分析（工期、资源）
  3. 评审批准
  4. 更新文档
- **变更控制**：开发阶段变更需项目经理审批

## 2. 项目计划

### 2.1 里程碑
```
项目启动   → 需求评审   → 设计评审   → 开发完成   → 测试通过   → 上线发布
Week 0       Week 1       Week 2       Week 6       Week 8       Week 10
```

### 2.2 任务分解
- **WBS（工作分解结构）**
  - 一级任务：需求分析、架构设计、开发实现、测试验证、上线部署
  - 二级任务：按模块拆分
  - 三级任务：具体开发任务，粒度1-3天

### 2.3 资源分配
| 角色 | 人数 | 投入比例 |
|------|------|----------|
| 产品经理 | 1 | 50% |
| 架构师 | 1 | 30% |
| 后端开发 | 3 | 100% |
| 前端开发 | 2 | 100% |
| 测试工程师 | 2 | 100% |
| 运维工程师 | 1 | 20% |

## 3. 迭代管理

### 3.1 Sprint规划
- **周期**：2周一个迭代
- **容量**：按团队速率（Velocity）规划
- **优先级**：P0 > P1 > P2 > P3

### 3.2 每日站会
- **时间**：每天上午10:00，15分钟
- **内容**：
  - 昨天完成什么
  - 今天计划什么
  - 遇到什么阻碍

### 3.3 迭代评审
- **Demo演示**：展示已完成功能
- **回顾会议**：总结问题与改进点
- **速率更新**：统计本迭代完成故事点

## 4. 风险管理

### 4.1 风险识别
| 风险类型 | 风险描述 | 概率 | 影响 | 应对措施 |
|----------|----------|------|------|----------|
| 技术风险 | 新技术栈学习成本 | 中 | 高 | 提前技术预研 |
| 人员风险 | 核心开发离职 | 低 | 高 | 知识文档化 |
| 需求风险 | 需求频繁变更 | 高 | 中 | 变更控制流程 |
| 依赖风险 | 第三方接口延期 | 中 | 中 | 并行开发 + Mock |

### 4.2 风险跟踪
- **周报更新**：风险状态变化
- **升级机制**：高风险项上报管理层

## 5. 质量管理

### 5.1 质量目标
- **代码质量**：
  - 代码审查覆盖率 100%
  - 单元测试覆盖率 ≥ 80%
  - 代码规范扫描通过率 100%

- **交付质量**：
  - 线上Bug率 < 2个/千行代码
  - P0/P1 Bug必须当天修复
  - 用户满意度 ≥ 4.5分

### 5.2 质量检查点
```
代码提交 → 自动化测试 → 代码审查 → 集成测试 → 预发布验证 → 生产发布
  ✓          ✓            ✓          ✓           ✓            ✓
```

## 6. 沟通管理

### 6.1 会议制度
| 会议类型 | 频率 | 时长 | 参与方 |
|----------|------|------|--------|
| 项目启动会 | 项目初期 | 2小时 | 全员 |
| 需求评审会 | 按需 | 1-2小时 | PM+开发+测试 |
| 技术评审会 | 按需 | 1小时 | 开发+架构 |
| 每日站会 | 每天 | 15分钟 | 开发团队 |
| 周会 | 每周 | 1小时 | 全员 |
| 迭代评审会 | 每迭代 | 1小时 | 全员 |

### 6.2 文档管理
- **文档清单**：
  - 需求文档（PRD）
  - 技术方案
  - 接口文档
  - 数据库设计文档
  - 测试用例
  - 部署文档
  - 操作手册

- **存储位置**：统一Wiki或文档系统

## 7. 变更管理

### 7.1 代码变更
- **小改动**（< 500行）：代码审查通过即可合并
- **大改动**（≥ 500行）：需技术评审 + 分阶段提交

### 7.2 配置变更
- **流程**：
  1. 提交变更单
  2. 技术负责人审批
  3. 先改预发布环境验证
  4. 再改生产环境

### 7.3 数据库变更
- **DDL变更**：
  - 提前3天提交DBA审批
  - 低峰期执行
  - 必须有回滚方案

## 8. 发布管理

### 8.1 发布计划
- **发布窗口**：
  - 例行发布：每周三晚上21:00-23:00
  - 紧急发布：需技术总监审批

- **发布检查清单**：
  - ✓ 代码审查通过
  - ✓ 单元测试通过
  - ✓ 集成测试通过
  - ✓ 预发布环境验证
  - ✓ 数据库变更脚本准备
  - ✓ 配置文件更新
  - ✓ 回滚方案准备

### 8.2 发布流程
```
代码冻结 → 构建打包 → 预发布部署 → 验证测试 → 灰度发布 → 全量发布 → 监控观察
```

### 8.3 发布回滚
- **触发条件**：
  - 错误率超过5%
  - P0 Bug影响核心功能
  - 性能下降超过30%

- **回滚时限**：发现问题后10分钟内完成回滚

## 9. 度量指标

### 9.1 开发效率
- **速率（Velocity）**：每迭代完成故事点数
- **周期时间（Cycle Time）**：需求从开始到完成的时间
- **吞吐量（Throughput）**：单位时间完成需求数

### 9.2 质量指标
- **缺陷密度**：Bug数/千行代码
- **缺陷修复时间**：Bug从发现到关闭的时间
- **测试覆盖率**：单元测试、接口测试覆盖率

### 9.3 交付指标
- **按时交付率**：按计划完成项目比例
- **需求变更率**：变更需求数/总需求数
- **用户满意度**：用户评分

## 10. 项目复盘

### 10.1 复盘时机
- **迭代复盘**：每个迭代结束后
- **项目复盘**：项目上线后1周内

### 10.2 复盘内容
- **做得好的**：值得推广的经验
- **做得不好的**：需要改进的地方
- **改进措施**：具体行动计划

### 10.3 复盘模板
```markdown
# 项目复盘报告

## 项目概况
- 项目名称：xxx
- 计划周期：10周
- 实际周期：12周
- 投入人力：20人月

## 关键指标
- 按时交付率：80%
- 需求变更率：15%
- 线上Bug数：3个
- 用户满意度：4.6分

## 做得好的
1. 技术选型合理，性能达标
2. 测试覆盖充分，质量可控

## 待改进的
1. 需求变更频繁，影响进度
2. 前后端联调时间不足

## 改进措施
1. 加强需求评审，控制变更
2. 提前定义接口规范
```

## 11. 禁止事项

### 11.1 项目管理禁忌
- ❌ 禁止口头需求，必须文档化
- ❌ 禁止跳过评审直接开发
- ❌ 禁止私自承诺发布日期
- ❌ 禁止隐瞒项目风险
- ❌ 禁止未经测试直接上线
